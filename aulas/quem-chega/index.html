Aula 6 · 18 min

Identificar quem chega: Web Bot Auth e signed agents (rascunho IETF)

User-Agent qualquer um escreve. Web Bot Auth é a proposta do IETF para o bot assinar cada pedido com uma chave publicada numa URL dele. Ainda é rascunho (-00, setembro de 2026). Nesta aula você confere uma assinatura contra o vetor do draft e vê num servidor local o que ela prova e o que não prova.

Começar a aula

Nesta aula você vai

  1. 1HTTP Message Signatures (RFC 9421) e o que o draft acrescenta
  2. 2O vetor de teste do draft refeito byte a byte
  3. 3Componentes cobertos, validade e replay
  4. 4Identidade não é autorização: a política continua sua

Objetivo: conferir uma assinatura Web Bot Auth com o vetor do draft e verificar pedidos assinados num servidor local, sabendo o que a assinatura não prova.

01 · Do agente que assina à política do site

draft-ietf-webbotauth-httpsig-protocol-00 (01/09/2026). Clique em cada etapa.

Clique em cada bloco do diagrama para ver o que ele faz.

Rascunho de grupo do IETF (Cloudflare e Google), expira em 05/03/2027. Não é RFC.

02 · O vetor do draft, refeito

Apêndice E.2.1: Ed25519 com a chave de teste pública do RFC 9421 (B.1.4). Só node:crypto, nenhum pacote.

Terminal · vetor
cd ~/projetos/formacao-webmcp-seguranca-v72/kit
node scripts/wba.mjs vetor; echo "saída: $?"
Exemplo do repositório
== node v24.13.0 · draft-ietf-webbotauth-httpsig-protocol-00 (01/09/2026)
keyid calculado: poqkLGiymh_W0uP6PZFw-dvez3QJT5SolqXBCW38r0U · confere
assinatura: RdNFx5Bj6au3YgAMQL/RzmUl… · confere
vetor E.2.1: confere
saída: 0

Ed25519 é determinístico: mesma chave e mesma base dão a mesma assinatura. Se a sua implementação refaz o vetor, ela monta a base de assinatura do jeito do draft. A chave de teste nunca vai para produção (anexo C.12 do draft).

03 · Agente assina, origem confere: sete casos

Chave nova a cada execução. A origem já tem o diretório do agente, como o draft permite (§4.4); nada sai da sua máquina.

Terminal · demo
cd ~/projetos/formacao-webmcp-seguranca-v72/kit
node scripts/wba.mjs demo; echo "saída: $?"
Exemplo do repositório
== node v24.13.0 · draft-ietf-webbotauth-httpsig-protocol-00 (01/09/2026) · origem http://127.0.0.1:36913
1 · sem assinatura → anônimo: sem assinatura (a política do site decide)
2 · assinado, válido → identificado: https://agente.exemplo (chave gw6T0rIc…)
3 · mesma assinatura em outro caminho → recusado: assinatura não confere
4 · assinatura vencida → recusado: assinatura vencida
5 · chave que a origem não conhece → recusado: chave desconhecida para https://agente.exemplo
6 · replay dentro da validade → identificado: https://agente.exemplo (chave gw6T0rIc…)
7 · assinatura mínima (só @authority) usada em /admin → identificado: https://agente.exemplo (chave gw6T0rIc…)
7/7 casos como esperado · replay dentro da validade: aceito
saída: 0

Os casos 6 e 7 são o aviso do draft (§5.2): dentro da validade, quem viu o pedido pode repeti-lo; e uma assinatura que cobre só @authority vale para qualquer caminho do site. Por isso: validade curta e @method + @path cobertos, e a origem pode exigir esses componentes.

04 · Onde isso já aparece

1. Cloudflare

Desde 01/07/2026, agentes assinados com Web Bot Auth contam como Verified, com um campo novo: Direct (um operador só) ou Intermediary (serviço que muitos usuários comandam).

2. Intermediário

No Intermediary, você pode confiar no operador e não em cada usuário que dirige o agente. A Cloudflare chama isso de confiança transitiva.

3. O seu site

Anônimo continua existindo: assinar é escolha do bot. Escreva a sua política para os três casos: anônimo, assinado e conhecido, assinado e desconhecido.

4. Junto com robots

robots.txt diz para que finalidade cada bot pode vir; a assinatura diz quem é. O robots a fundo é da Formação inemaSEO.
